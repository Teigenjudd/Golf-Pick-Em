# Poold — Project Reference

## Brand

**Name:** Poold
**Domain:** getpoold.app
**Tagline:** "Make it interesting."
**Descriptor:** "Drop your picks. Jump in the pool. Make it interesting."

**Voice:** Casual, confident, social, competitive. Sunday afternoon energy. Group chat popping off. Everyone's got something on the line.

**NOT:** Sportsbook. ESPN. Corporate fantasy app. Anything that takes itself too seriously.

**Theme system:** Two registers — *general* (auth, dashboard, admin — brand-level, sport-agnostic) and *sport-specific* (pool detail + picks page — theme swaps per sport type). Golf is fairway green/gold. CFB's register — "Varsity Navy" (navy `#101C3D→#0A1229` header gradient, brick `#D6291B` accent, green `#2E8F4F` cover/win — constants in `src/theme/cfb.js`) — is locked and applied to both player-facing CFB pages (`/cfb/pool/:id`, `/cfb/pool/:id/picks`), each now carrying its full real content (leaderboard + weekly picks builder, including the read-only locked/graded card). Future sports get their own theme applied only on those two pages.

**Page inventory:** Full page-by-page breakdown of data, layout, and functionality lives in `docs/PAGES.md`. **Keep it in sync:** any time a page's data, layout, functionality, or design notes change, update the corresponding section in `docs/PAGES.md` as part of the same PR.

## Working Style

When given a substantial instruction or multi-step request, respond with a short summary (under 100 words) of what you understand and plan to do — then wait for approval or refinement before writing any code. Skip this for simple one-liner fixes where the intent is unambiguous.

**Audience / how to explain things:** The user is a **data scientist/analyst**, comfortable with **intermediate Python and OOP**, but **not a web/backend/frontend/infra developer**. Explain things **as simply and plainly as possible while staying accurate**. When a concept is genuinely complex or uses unfamiliar web/backend/DB/DevOps jargon (RLS, schemas, PostgREST, edge functions, FKs, embedding, CORS, etc.), **define it in simple terms first, then proceed** — don't blaze ahead assuming it's understood. Use an analogy only when it genuinely makes something clearer; don't force everything into Python/data metaphors. SQL and Python can be assumed; web/infra plumbing cannot.

### Signature Element: The Scorecard Expand

On the leaderboard (TournamentDetail), each row expands via a `flex` container where the first child is a `w-[3px] bg-gold` bar — the gold stripe that runs the full height of the expanded content. Inside: tier numbers as small `w-5 h-5 rounded-full bg-fairway/80` circles with `text-cream` numbers (hole-marker style), player names, and tabular scores. The last row is a "TOTAL" row with `border-t border-warm-200`.

### Tournament Badges (SportBadge)

The shield/tombstone emblem on every pool surface (dashboard tile, join preview, picks header, leaderboard header). **Badge color is a system, not a constant:** background + border are stored per tournament in `badge_config` and encode **prestige + geography** — each major has a signature palette (The Open = navy `#162258` + gold `#C9A368`, the Masters = `#004F2D` + `#E8C872`), flagship/playoff events use dark grounds with prestige gold, and tour stops follow regional families. Shape and type never vary.

`badge_config` is one object per event: `{ line1, line2, bg, border }`. Line 1 always renders cream; line 2 always renders in the badge's own border color; line 1's **font size is derived from its character count** by `SportBadge`, never stored, so a long abbreviation can't overflow the shield. Seed data for all 48 tournaments lives in `public.pga_event_badges` (keyed by Slash Golf `tourn_id`) and is **copied** onto `golf.event_details.badge_config` at pool creation — so editing a seed row does not change pools that already exist. Full spec in `DESIGN_SPEC.md` §Sport badge and `docs/PAGES.md` §SportBadge.

### Page Header Pattern

Pages with a primary subject (TournamentDetail, Dashboard) use a `bg-fairway` header band with `text-cream` content. Auth/utility pages (Login, Join) use a centered layout on `bg-cream` with a large `font-display font-bold text-fairway` wordmark.

### Copy Guidelines

- Empty leaderboard: "Leaderboard opens once the first tee times go off."
- No picks submitted: "No cards in yet."
- Pool status → "Close Pool" (not "Mark Complete")
- Picks locked notice: "Picks are locked for this pool."
- Picks confirmed: "Your picks are in — you can update them before the round locks."
- Score display: negative = red (birdie), positive = charcoal, 0 = "E" in charcoal/medium

## Architecture Summary

> **Doc rule:** this section describes how the system works *now*, not how it got there. No dates, no PR numbers, no "shipped X then Y" — the changelog is `git log` and the merged PRs. If a line only makes sense with a date attached, it's a changelog line and belongs in a PR, not here. Keep each bullet to current-state facts + a file pointer.

- **Brand:** App is called Poold, domain is getpoold.app (deployed on Netlify).
- **Data model (post multi-sport migration, June 2026):** Two Postgres schemas. `public` holds the sport-agnostic core (`profiles`, `sports`, `events`, `pools`, `pool_participants`, `pool_standings`); the `golf` schema owns golf's contest structure (`event_details`, `tiers`, `tier_players`, `picks`, `leaderboard_cache`). `public.events` is the hinge — many pools can share one event; the field (tiers/players) and leaderboard cache are event-level. **All golf data access goes through `src/lib/golf.js`** — the only file that calls `supabase.schema('golf')`. It stitches pool + event_details back into the old flat "tournament" shape (`mergePoolView`) so screens didn't have to change. Queries across the public/golf boundary are split and joined in JS, never nested PostgREST embeds (Phase 0 decision — see `docs/MULTI_SPORT_MIGRATION.md`). Legacy `public.tournaments/tiers/tier_players/picks/leaderboard_cache` tables still exist but are dead — never read or write them (Phase 5 will drop them).
- **Auth:** Two sign-in methods, both on `Login.jsx` behind a "Sign-in link" / "Password" mode toggle — the magic link (`signInWithOtp`, still the default tab) and email+password (`signInWithPassword`). `AuthCallback.jsx` (link flow only) redirects to `/dashboard` or `/join/:code` — no status gate; the password flow has no callback step, it relies on the existing `AuthContext`/`RootRoute` redirect once the session lands. `ProtectedRoute` checks `user` exists; `AdminRoute` checks `profile.role === 'admin'`. Profiles auto-approve on creation via DB trigger. Join code + a working sign-in method is the access gate. There is no separate password-reset flow: a user who forgets their password signs in with a link and sets a new one from the "Password" card on `/profile` (`src/lib/profile.js` — `PASSWORD_MIN = 8`, `validatePassword`, `savePassword` wrapping `supabase.auth.updateUser({ password })`), with no "current password" step — being signed in via either method is treated as sufficient authorization to set a new one. This is a deliberate call, not an oversight (see `agents/pm/DECISIONS.md`, 2026-08-31): it avoids adding a second branded auth email/token flow. Two related Supabase Dashboard settings (Authentication → password minimum length, and the "Secure password change"/reauthentication toggle) still need founder verification against this design — not yet done, tracked as BACKLOG A11. **User-facing naming (2026-07-17, PR #36):** all product copy calls the link method a "sign-in link" (Login.jsx, Join.jsx, Privacy.jsx — button reads "Email me a sign-in link") — deliberately not "invite" (that word is reserved for the pool join-code flow). Supabase's own dashboard template category is still fixed-labeled "Magic Link" (their internal admin-only name); that label is never user-facing. **Auth email delivery (live 2026-07-16):** Supabase sends through custom SMTP — Resend, verified on `getpoold.app` (SPF/DKIM/DMARC), sending as `login@getpoold.app` via `smtp.resend.com` — instead of the rate-limited default Supabase sender. The branded Magic Link template (fairway/cream/gold) is live in the Supabase dashboard; `supabase/templates/magic_link.html` is the versioned copy kept in sync by hand. `signInWithOtp` is still the app's only auth-**email** trigger (`Login.jsx`, `Join.jsx` — no signUp/reset/reauth/invite/email-change; password sign-in and `updateUser({ password })` send no email), so Magic Link remains the only one of Supabase's six templates that ever fires. (Closes BACKLOG C7; the separate inbound-mail item, BACKLOG A7 for `privacy@getpoold.app`, is still open — interim mitigation shipped 2026-08-10, see the Legal bullet below.) **Header dark-mode fix (2026-07-17, PR #36):** the email's fairway header band is now a baked PNG (`public/email-header.png`, served from `getpoold.app/email-header.png`, rendered via `npm run og:email` → `scripts/og/build-email-header.mjs` + `scripts/og/email-header.html`, mirroring the OG-card toolchain) instead of live HTML text — Gmail-app and Outlook-mobile force-invert colors in dark mode and ignore the template's `color-scheme` meta tags, which flipped the fairway band to light mint; image pixels aren't recolored by that inversion. The `<img>` carries cream Barlow-styled alt text as the images-off fallback; the sign-in button below stays real HTML (tappable link, not an image map). Regenerate and re-commit the PNG (then reverify the URL is live) any time the header's brand colors or tagline change — it's no longer a plain-text edit.
- **Display names:** `profiles.display_name` is the *only* identity shown to other players — no email appears on any player-facing screen (`/admin/users` is the exception, via the admin-gated `admin_list_users()` RPC — role management, formerly a tab on `/admin`, now lives on this sport-agnostic page). The signup trigger deliberately leaves `display_name` NULL; `ProtectedRoute` and `AdminRoute` bounce any unnamed account to `/welcome`, which is where it picks one. Existing users change it at `/profile`, reached from the header avatar (no bottom nav — see below). `display_name_set_at` records that a *human* chose the name — it is stamped by a `BEFORE UPDATE` trigger, never by the client, and a NULL stamp means the row still carries the email-derived name the old trigger wrote (`split_part(email, '@', 1)` — the leak this closes). The nudge toward setting one is now a small gold dot on the header avatar (`ProfileMenu`, `src/pages/Dashboard.jsx`) when `display_name_set_at` is NULL, replacing the old `BottomNav` bubble (`BottomNav` is deleted — Dashboard and Profile no longer render a bottom tab bar; Profile access is the header avatar, which opens a Profile/Admin dropdown for admins). Writes still go through the plain `GRANT UPDATE (display_name)` from A1; a `CHECK` constraint bounds the name at 2–24 chars (`src/lib/profile.js` mirrors it client-side).
- **Avatars / Supabase Storage (first use):** `profiles.avatar_url` (text, nullable) follows the same self-service column-grant pattern as `display_name` — `GRANT UPDATE (avatar_url)` + the existing `auth.uid() = id` policy — plus `admin_set_avatar_url(target_user, url)` (mirrors `admin_set_role`) for the admin-overrides-anyone case a plain grant can't reach; `admin_list_users()` now also returns `avatar_url`. Uploads land in the app's first Supabase Storage bucket, `avatars` (public read, 5MB cap, jpeg/png/webp only — enforced server-side by the bucket config, not just the client-side `validateAvatarFile` check); storage RLS on `storage.objects` pins writes to your own `{user_id}/` folder, with an `is_admin()` carve-out so admins can write into anyone's folder. `uploadAvatarForUser(targetUserId, file)` (`src/lib/profile.js`) uploads to a fixed `{user_id}/avatar.<ext>` key with `upsert: true` (a same-extension re-upload replaces cleanly; switching extensions orphans the old file — known low-severity nit, not fixed) and stamps a `?v=<timestamp>` cache-buster onto the URL that actually gets stored in `avatar_url`. A `CHECK` constraint (`profiles_avatar_url_is_our_storage`, `supabase/migrations/20260831030000_lock_avatar_url_to_storage.sql`) requires the column be null or start with this project's own storage public-URL prefix — the column-grant pattern only ever checked *who* could write, never *what*, so without this a user could bypass the uploader and point their avatar at an arbitrary external image (tracking-pixel risk). The bucket's public-read setting (anyone with the URL can fetch an avatar, not just pool members) is a deliberate, revisit-if-it-ever-matters call, not an oversight — see `agents/pm/DECISIONS.md`. Shared render: `src/components/Avatar.jsx` (the photo if `avatar_url` is set, else the existing initials-on-a-flat-color circle — one color, deliberately not a per-user palette) is used everywhere a player shows up: `/profile`, the Dashboard header `ProfileMenu`, `/admin/users`, and both leaderboard rows (`Standings.jsx`, `CfbStandings.jsx`), which moved their rank number out of the circle into a plain numeric rail on the row's left edge so the circle could hold the avatar instead.
- **Picks:** Auto-confirmed on submit (`status: 'confirmed'`). Re-submit deletes existing picks and re-inserts. RLS enforces integrity (one pick per tier via a unique constraint; the tier must belong to the tournament and the player must exist in that tier) and privacy (you only see other participants' picks after lock/lock_time).
- **Prize pool (optional):** `public.pools.stake_amount` (numeric) + `payout_structure` (jsonb — ordered % per placement, enforced to sum to 100 at creation). The leaderboard renders a `PrizePoolWidget`: total = `stake × participants`, distributed by placement in whole dollars (rounding remainder folded into 1st). Omitted when no stake is set.
- **Demo:** Public, no-auth showcase at `/demo` (routes outside `ProtectedRoute`) — now a golf/CFB sport chooser, not golf-only. Golf demo (`/demo/tournament`, `/demo/picks`) runs off a static fixture (`src/demo/demoData.js`) — a snapshot of public golf data with fabricated participants; `DemoProvider` holds the visitor's picks in memory only. CFB demo (`/demo/cfb`, `/demo/cfb/picks`) mirrors it: fixture `src/demo/demoCfbData.js` simulates a season one week in (Week 1 graded via the real `projectSeasonStandings`/`shapeCard` scoring engine, not hand-typed; Week 2 open with no picks yet), `DemoCfbContext` holds the visitor's in-progress Week 2 card in memory, and `DemoCfbPoolDetail.jsx`/`DemoCfbPicks.jsx` render through the same real CFB components the live pages use (`CfbStandings`, `CfbWidgets`, `CfbGameCard`, etc.) rather than reimplementing them. Neither demo ever imports `supabase` or touches the DB.
- **Shared UI:** Both the live pool pages and the demo render through the same components so they can't drift apart (change once, both update):
  - **Page shells** in `src/components/pool/` — `PoolHeader` (gradient leaderboard header + SportBadge), `PicksHeader` (gradient picks header), `PicksSubmitBar` (sticky submit), `StandingsCard` (section label + standings card shell), `WidgetGrid` (widget row). The pages pass their own data source (Supabase vs `src/demo/` fixture); the chrome is identical. When you restyle a pool/picks page, edit the shell — not the page.
  - **Leaf components** — leaderboard widgets + scorecard-expand standings in `src/components/leaderboard/`; the tier/player pick grid in `src/components/picks/TierPicker.jsx`.
  - Slash Golf data helpers (`parseScore`, `normalizeName`, `unwrapNumber`) are exported from `src/utils/scoring.js`; money/ordinal formatting in `src/utils/format.js`.
- **Leaderboard:** Cached in `golf.leaderboard_cache` (one row per event — all pools on an event share it). Poll via `poll-leaderboard` edge function (pg_cron on tournament weekends, or admin "Refresh Now" button — 3/event limit via `golf.event_details.manual_refresh_count`). The automatic cron poll **dedupes by Slash Golf `tourn_id`**: because `createGolfPool` mints a separate event per pool, many pools on the same real tournament are many events sharing one `slash_golf_tournament_id`, so the poll fetches the API **once per tournament** and fans the identical payload into every event's cache row — API spend scales with tournaments, not pools (odds in `tier_players` are never touched; only live scores are shared). The manual "Refresh Now" stays scoped to its single event.
- **Scoring:** `src/utils/scoring.js`. Scores are relative-to-par strings (`"-12"`, `"E"`, `"+4"`, `"-"`). `parseInt` handles signed strings; `"E"` → 0; `"-"`/null → null (not started). WD and CUT both penalized +20 and remain in scoring pool. Best N of M scores count.
- **Player name matching:** Slash Golf and The Odds API spell the same golfer differently (`Tom Kim` vs `Joohyung Kim`, `Højgaard` vs `Hojgaard`), and they share no player ID — so odds are joined onto the field **by name** at pool creation. `src/utils/playerMatch.js` resolves in layers: normalize (`normalizeName` transliterates atomic letters like `ø` that NFD won't decompose) → surname + first-initial fallback → the alias table in `src/utils/nameAliases.js`. An ambiguous fallback is **refused**, not guessed — a missing price shows as `N/A` and is recoverable; a wrong price silently mis-tiers the field. Full spec and the procedure for extending the alias table each season: `docs/NAME_MATCHING.md`.
- **APIs:**
  - Slash Golf via RapidAPI — proxied through `slash-golf-proxy` edge function (field + live leaderboard). API key stored as Supabase secret, never exposed to browser.
  - The Odds API — proxied through the `odds-proxy` edge function (admin-only; key stored as the `ODDS_API_KEY` Supabase secret, never exposed to the browser). Outright winner markets for majors only. `src/lib/oddsApi.js` still does the median-price / canonical-name pooling client-side — only the fetch is server-side.
  - Open-Meteo — weather forecast, called client-side on TournamentDetail load. No key required.
  - Nominatim — course location lookup at tournament creation time only, called client-side. No key required, but requests carry an `email=` param per Nominatim's usage policy (the browser can't set a custom User-Agent). Free-text query is `courseName, city, state`, falling back to a town-level `city, state` query if the specific query returns nothing. Replaced Open-Meteo's geocoder 2026-07-16 (F3 in `docs/BACKLOG.md`, now done) — Open-Meteo matched on the `name` field only and couldn't resolve course names or "City, State" strings, so UK links courses (The Open @ Royal Birkdale) got null lat/lon and a blank weather widget.
- **Weather:** `latitude`/`longitude` stored on `golf.event_details`, geocoded via Nominatim at creation. Open-Meteo forecast called client-side on TournamentDetail load. Omitted silently if `latitude`/`longitude` is null.
- **Cron schedule:** 4 pg_cron jobs (`poll-thursday` through `poll-sunday`), each polling every 20 minutes (`*/20 11-23`) during the 7am–8pm ET window. Arm/disarm them from the **Admin panel** (`/admin` → "Leaderboard polling" toggle), which calls the `admin_start_leaderboard_polling()` / `admin_stop_leaderboard_polling()` RPCs; these read the `CRON_SECRET` the jobs send from **Supabase Vault** (`vault` secret `cron_secret`), which must equal the `poll-leaderboard` edge function's `CRON_SECRET` env or every poll silently 401s. The raw `supabase/cron-schedule.sql` (placeholder secret) still works as a manual fallback. **CFB has a parallel admin toggle** (`/admin/cfb` → "CFB polling" card, `admin_start_cfb_polling()` / `admin_stop_cfb_polling()` / `admin_cfb_polling_status()` in `supabase/migrations/20260814000000_admin_cfb_polling_controls.sql`) arming three `cfb-*`-prefixed jobs windowed to the Aug–Jan season: `cfb-lines` (hourly slate/spread refresh), `cfb-scores` (every 2 min during game hours, every in-season day), and `cfb-grade` (twice-daily grading backstop) — the job-name prefix keeps golf's `poll-*` jobs and CFB's `cfb-*` jobs from ever touching each other. Not yet applied to prod or armed — see `docs/CFB_BUILD_PLAN.md` PR9.
- **Link previews (invite unfurls):** Crawlers (iMessage, WhatsApp, Slack, Discord, Twitter) fetch a URL and read `<head>` **without running JavaScript** — so in an SPA, meta tags written by React are invisible to them, and a join link unfurls as a bare URL. `/join/*` is therefore served through a **Netlify edge function** (`netlify/edge-functions/join-preview.js`, wired in `netlify.toml`), which rewrites the OG block between the `<!-- og:start -->` / `<!-- og:end -->` markers in `index.html` *before the HTML goes out*. Pool data comes from `public.pool_preview(code)` — a `SECURITY DEFINER` RPC with a fixed projection, granted to `anon`, **so the edge function never holds a service-role key** (that key bypasses RLS everywhere; it is not worth risking for a preview card). Every failure path is silent: bad code, timeout, or missing env falls back to the default tags. Card image is `public/og-default.png`, regenerated with `npm run og` (headless Chrome renders `scripts/og/card.html`, so the real brand fonts are used). The default card is styled off the **general** register (sand `#F8F0E4` background, brand-rust `#C14A18` wordmark — the actual current Login/Dashboard tokens, not the fairway/gold pool-detail theme) with one generic shield badge per sport Poold runs today (Golf, CFB) rather than specific tournament badges — it's the shared front door for every sport's invite unfurl, not a golf-only card. - **Security:** Audit items C1–C4 and backlog items A1–A2 are fixed. The pattern to know: **RLS is row-level and cannot restrict columns, so column access is controlled by GRANTs, which are evaluated *before* any policy runs.** `profiles` is column-locked in both directions — `anon`/`authenticated` can SELECT only (`id, display_name, avatar_url, role, status, created_at`) and UPDATE only (`display_name`, `avatar_url`) — the latter additionally bounded by a `CHECK` constraint (see the Avatars bullet above), since a GRANT only ever restricts *who* can write a column, never *what* they write. Anything privileged goes through a `SECURITY DEFINER` RPC that re-checks `is_admin()` itself: `admin_list_users()` (reads email + avatar_url), `admin_set_role()` (writes role; also refuses a self-role-change so a sole admin can't lock themselves out), `admin_set_avatar_url()` (writes another user's avatar), and `admin_start_leaderboard_polling()` / `admin_stop_leaderboard_polling()` / `admin_polling_status()` (arm/disarm/read the poll cron jobs; touch the `cron` + `vault` schemas the browser role can't). Because `is_admin()` gates on `role='admin'`, a future non-admin commissioner role is already refused by these at the server. **Never add a plain `.update()` on `profiles.role` — it will fail, by design.** Still open: A3 (manual-refresh cap is client-side only), A4 (edge functions allow all origins), A5 (`join_code` readable for any non-draft pool). The full ranked backlog lives in `docs/BACKLOG.md` (supersedes `docs/AUDIT.md`).
- **Sport #2 = CFB (cut over to prod, no real users yet):** college football, weekly against-the-spread + season-cumulative, fully siloed from golf — its own `cfb` Postgres schema (`event_details`, `weeks`, `games`, `picks`), its own `src/lib/cfb.js` seam (the only file calling `supabase.schema('cfb')`), its own scoring engine (`src/utils/cfbScoring.js`, mirrored server-side at `supabase/functions/_shared/cfbScoring.ts` — shared fixtures keep the two in parity), and its own data provider (CollegeFootballData). Only the shared `public.pool_standings` `{user_id, rank, total, display}` output shape is common with golf. **What exists today:** the full backend (schema + RLS + `cfb.cfb_submit_week_picks`, the whole-card submit RPC that is the *only* write path onto `cfb.picks`); `cfb_submit_week_picks` also enforces a **per-game kickoff lock** on top of the week-level `lock_time`: once a game's `kickoff_at` has passed, its slot in a submitted card must exactly match what's already on file (unchanged carry-forward is fine; a new/changed/dropped pick on it is rejected) — `src/utils/cfbCard.js`'s `gameHasStarted` mirrors this client-side so `CfbGameCard` greys out started games, and the "Edit picks" reset flow (`?reset=1`, `CfbPicks.jsx`/`CfbPoolTile.jsx`) only clears not-yet-started games, carrying forward any already-started pick pre-filled and locked rather than wiping the whole card (`supabase/migrations/20260817000000_cfb_game_kickoff_lock.sql`; rule of record in `docs/CFB_FORMAT.md`); the grader (`grade-cfb-week` edge fn, the first writer of `public.pool_standings`); two CFB pollers (`poll-cfb-lines` hourly for slate/spreads, `poll-cfb-scores` for live in-game scores — both talk to CFBD directly) plus `cfd-proxy` (the admin-JWT proxy); admin pool-creation + weekly-ops pages (`/admin/cfb*`); the player Pool Detail / leaderboard page (`/cfb/pool/:id`, Varsity Navy theme in `src/theme/cfb.js`); and the weekly picks page (`/cfb/pool/:id/picks`), which now covers both the interactive builder (5 ATS picks + optional double-down + mandatory underdog on 6 distinct games, live client-side validity, submit via `cfb_submit_week_picks`) and, once the week locks, a frozen read-only card (locked/submitted, locked/auto-filled, graded) rendered by `CfbCardReadonly`. Week resolution honors a locked `?week=N` deep-link, else the earliest open week, else the latest locked week. The read-only card and the pool-detail scorecard-expand share one row renderer (`CfbCardRows`) and one grading transform (`shapeCard`, `src/utils/cfbCard.js`) so the two views can't drift; a double-down row shows the effective line as a `DD → +4` chip. A missed deadline needs no admin action: `cfb.autofill_week(week_id)` (pure-DB `SECURITY DEFINER` RPC, no CFBD call) drops a random valid card — 5 ATS on 5 distinct games + 1 underdog on a 6th distinct **underdog-eligible** game, never a double-down (a missed deadline forfeits it) — into every non-draft participant's empty week; a pick'em (spread-0) game has no underdog side, so it's excluded from the underdog slot but still usable as an ATS pick. `cfb.process_locked_weeks()` flips a week's status to `locked` once its `lock_time` passes and calls `autofill_week` for it, and is armed as an always-on `cfb-lock-autofill` pg_cron job (every 10 min, in-season, `supabase/migrations/20260814020000_cfb_lock_autofill_cron.sql`) that **is live in prod today** — pure SQL, zero API spend, so it runs independent of the billable CFBD pollers (also live — see below). `grade-cfb-week` also calls `autofill_week` as a grading backstop, and the admin "Auto-fill missing cards" button on `CfbPoolOps.jsx` remains as a manual override. (Picks already closed for editing at `lock_time` on every read/write path before this; what was missing, now fixed, was the visible status flip and the fill itself.) A per-week `pg_advisory_xact_lock` inside `autofill_week` keeps the cron, the grader backstop, and the admin button from racing into a double-filled card. CFB uses **per-pool events** like golf; graders and pollers dedupe CFBD calls by real `(season, week_number)` — with one carve-out: CFBD does not give our Week 0 (the pre-Labor-Day slate, e.g. TCU/UNC) its own week number, lumping those games into the same raw `week: 1` as the following weekend's real Week 1, so `_shared/cfbSlate.ts` resolves week 0 vs. 1 by kickoff date (`isWeekZeroGame`, a manual per-season UTC window in `WEEK_ZERO_WINDOW`) before either function matches a game to a week, and `grade-cfb-week` groups by that resolved week (`ourWeekToCfbdWeek`) so week 0 and week 1 share one CFBD `/games` call. An unconfigured season silently leaves that pool's Week 0 empty (BACKLOG C7). Spreads are the CFBD lines pulled automatically — CFB has no admin "odds" step. A CFB pool is now reachable through the normal join-code flow: `src/lib/pools.js` is a sport-neutral seam (reads/writes only `public.*`, never a per-sport schema) whose `getPoolByCode` resolves a join code's `sport_id` so `Join.jsx` can branch golf vs. CFB, and whose `joinPool` writes `pool_participants` explicitly — golf records that membership implicitly at pick-submit, but CFB's `cfb_submit_week_picks` RPC requires the row to already exist. The Dashboard also lists a user's CFB pools (`getMyCfbPools`, `CfbPoolTile`) alongside golf tiles; a locked/graded week routes from the Dashboard tile to the pool-detail expand (the primary card surface) — the picks page's read-only card is reachable by direct/bookmarked URL. The join-season cutoff (`pools.lock_time`) is enforced client-side only, fails closed if unset. Admin pool creation is sport-agnostic at the entry point: `/admin/create` (`CreatePoolChooser`) offers Golf or CFB, and a shared `AdminShell` (`src/components/admin/AdminShell.jsx` — sticky nav + `AdminSportSwitcher` Golf|CFB segmented control + a "Users & Settings" link to `/admin/users`) wraps both `/admin` and `/admin/cfb`; `getAdminPools` (`src/lib/golf.js`) filters to golf-only pools so CFB pools don't leak into the golf admin list. `/admin` is now a single pools list (its old Participants and Users tabs are gone — Participants has no replacement UI today, and Users moved to the sport-agnostic `/admin/users`); `getAllPools`/`removePoolParticipant` in `src/lib/golf.js` are unused leftovers from the deleted Participants tab. `setPoolStatus` (the `pools.status` write) lives in the sport-neutral `src/lib/pools.js` seam alongside `joinPool` — moved out of `src/lib/golf.js`, which no longer exports it — so both `/admin` and `/admin/cfb` import the same function; `/admin/cfb` has a one-way "Close Pool" button (flips a pool to `complete`, mirroring golf's admin panel — no re-open) next to each pool row. **Live in prod:** all four CFB edge functions (`poll-cfb-lines`, `poll-cfb-scores`, `grade-cfb-week`, `cfd-proxy`) are deployed, and all four CFB cron jobs — the three billable pollers (`cfb-lines`, `cfb-scores`, `cfb-grade`) plus the free `cfb-lock-autofill` — are armed and active; the schema migrations remain applied to prod because it still doubles as the CFB dev DB while there are no real users. A polling-toggle bug fixed in `supabase/migrations/20260815000000_fix_cfb_polling_toggle_scope.sql` had `admin_stop_cfb_polling()`/`admin_cfb_polling_status()` matching any `cfb-%` job name, which collided with `cfb-lock-autofill`; both RPCs now scope to the three billable job names explicitly.
